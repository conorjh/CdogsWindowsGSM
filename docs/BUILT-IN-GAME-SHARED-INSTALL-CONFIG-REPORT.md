# Built-in game shared-install and config-only report

**Source review:** 24 October 2026
**Status:** Source-derived inventory; not live game qualification.
**Related plan:** [Shared game installation implementation sub-plan](SHARED-INSTALLATION-PLAN.md)

## Findings at a glance

- The built-in dispatcher currently maps **57 game/provider identities**, including RedM as a subclass in `GTA5.cs`.
- The host declares config-only backup scopes for **20** built-ins: 10 Source titles, 7 GoldSrc titles, Call of Duty 1, Minecraft Bedrock, and Rust. These are explicit host file lists, not proof that a live server has been qualified.
- **Shared-install selection is enabled for 19 built-ins with config-only backup plans:** 10 Source titles, 7 GoldSrc titles, Call of Duty 1, and Minecraft Bedrock. This is code-path enablement, not live qualification. TFC is the only one with a tester-reported shared-install run; its update/recovery and remaining Alpha gates are still open.
- Rust remains config-only; its shared operations are blocked after a startup failure involving `Bundles\Bundles` under the per-instance working directory. Minecraft Bedrock now has both shared-install and config-only scopes, but neither has live qualification.
- The other **37** built-ins have no host-owned config-only scope and no enabled shared-install selection. A game-specific config template, provider implementation, or engine inheritance is not enough to infer either capability.
- Full-server backup remains the default. Config-only backup eligibility and shared-install eligibility are separate decisions.

## Evidence boundary and status terms

This review reads the current workspace source, especially `GameServer\Data\Class.cs`, `Functions\BuiltInGameCapabilities.cs`, `GameServer\Engine\Source.cs`, `GameServer\Engine\GoldSource.cs`, `GameServer\COD1.cs`, `GameServer\RUST.cs`, `GameServer\MCBE.cs`, and `BuiltInGameCapabilitiesTests.cs`. The tests verify host capability gates, declared backup paths, and shared-root lookup; they do not prove upstream game behavior, concurrent execution safety, or update safety.

- **Config-only scope declared** means the host has a fixed, validated file list for that provider. It does not mean every file a game owner might consider configuration is included, nor that the scope has passed a live qualification run.
- **Shared provider code** means the implementation has explicit binary-root/config setup paths. It does not make the game selectable; the host allowlist remains authoritative.
- **Private-only / no scope** means the current host does not offer that capability. It is not a claim that the game can never support it.
- Never infer a safe scope from file extensions, a shared engine class, or the presence of `CreateServerCFG()`.

### Exact support lists and implementation details

- The Source allowlist is the ten titles named above. Their shared-mode launch code builds an absolute `-game` path and passes per-instance config/map-cycle selectors, but runtime file selection and the complete writable-file set still need live proof. Add-on installation also needs to be routed to and locked against the correct shared root before it can be part of a supported workflow.
- The GoldSrc implementation uses SteamCMD dedicated-server AppID `90` with the selected mod. It keeps each `server.cfg` under that instance and uses a unique map-cycle filename in the shared mod directory because HLDS expects the map-cycle name relative to the mod. Verify the exact mod's fallback asset search and launch behavior rather than assuming all HLDS mods behave identically.
- `SDK2013` inherits the Source class but has an empty `Game` and a `-game <set me>` placeholder; it is intentionally absent from both the Source config-only set and the shared-install allowlist. Do not enable it by checking inheritance alone.
- COD1's shared path uses a shared `fs_basepath` and instance `fs_homepath`. Its MeatBots mod files are installed under the binary root, while the generated bot settings and editable server config are instance-owned; shared-install selection is enabled, but test the mod path independently from stock COD1 before treating it as qualified.
- Rust's existing private install/config-only path remains available. The shared-install implementation is explicitly unavailable and is not a candidate to enable by changing only the allowlist.
- Minecraft Bedrock (`MCBE.cs`) has a staged shared-binary installer and prepares `allowlist.json`, `permissions.json`, `behavior_packs`, `definitions`, `resource_packs`, and `structures` under an instance root when shared. The host now enables sharing and a config-only scope limited to `server.properties`, `allowlist.json`, and `permissions.json`. Managed settings are synchronized to `server.properties`, including the selected IPv4 port and the next port for IPv6. This is not live qualification: verify what must be copied versus kept immutable, prove world and other writable paths stay per-instance, and test concurrent starts, update locking, failure recovery, and backup/restore.

## Recommended qualification order

1. **Finish TFC**, the current live-test pilot: reproduce the two-instance checks and complete update, recovery, and rollback on a disposable install. Record binary hashes, config/map-cycle selection, writable paths, and errors.
2. **Qualify the other GoldSrc titles one by one.** Their selection is enabled, but shared HLDS behavior, mod-specific asset lookup, unique map-cycle operation, and update safety still need evidence per title.
3. **Test each Source title independently.** Observe the server loading its distinct instance config/map cycle; accepting command-line arguments is not enough. Do not treat one game's result as qualification for the rest.
4. **Test COD1 stock, then MeatBots.** The mod changes the binary-root/shared-content and per-instance-home behavior, so a stock result cannot qualify the mod.
5. **Qualify Bedrock's newly enabled shared-provider and config-only paths.** Verify which copied runtime directories are mutable, confirm world/config isolation, then test concurrent start, serialized update, failure recovery, and restore limited to the declared configuration files.
6. **Keep Rust shared mode blocked** until the bundle-root/per-instance-data design is solved. Continue using its existing config-only backup independently.
7. **For any new config-only candidate**, declare a small, explicit host-owned path list and test backup/restore against a full backup. Prove that restore changes only those files and never replaces shared binaries, worlds, saves, or unrelated runtime state.
8. **For every enabled shared-install candidate**, require exact-title evidence that two concurrent servers pass config/data isolation, lifecycle, update locking, rollback, and backup/restore checks before describing it as qualified. Do not use engine family or API method presence as qualification; keep any provider that fails its checks gated.
