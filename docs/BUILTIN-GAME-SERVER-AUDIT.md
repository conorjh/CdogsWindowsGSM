# Built-in Game Server Audit

- **Audit date:** 2026-10-21
- **Scope:** the 57 built-in entries registered in `CdogsWindowsGSM\GameServer\Data\Class.cs`. Plugins are excluded.

## Scope and confidence

This combines source-code/public-endpoint review with a limited runtime smoke test below; it is not a 57-game live integration run. No game servers were downloaded or launched. No Steam credentials, game licenses, CFX license key, or EULA acceptance were supplied. Per request, account-gated Steam operations are marked **N/A** rather than tested. Public Steam player-count endpoints do not require a Steam account.

There is no compile-time `IGameServer` contract: the application obtains each built-in dynamically and assumes that it provides the lifecycle methods and properties it uses. In the current source, all 57 registered entries have those methods directly or inherit them from an engine/helper class. That proves the code path is wired; it does **not** prove that its remote download, launch arguments, readiness, or shutdown work on a real server.

| Mark | Meaning |
|---|---|
| `I` | Implementation is present in this checkout; live game operation is unverified unless explicitly stated in the runtime smoke section. |
| `R` | A concrete source or current-endpoint risk is identified below. |
| `N/A` | Not tested because credentials/licensed data are unavailable, or no comparable public metric exists. |
| `—` | The adapter does not expose that optional query protocol. |

**Stop codes:** `Q` sends a game command; `W` requests window close or sends Ctrl+C; `K` kills the process directly; `M` depends on console mode (often `K` with embedded console enabled). The application itself waits up to 10 seconds after an adapter's stop request, then kills a still-running process.

## Runtime smoke test (2026-10-21)

After the request to test runtime behavior, the current Debug build was rebuilt with Visual Studio's .NET Framework MSBuild and exercised in-process against an isolated temporary root. The probe called the real `GameServer.Data.Class.Get` factory for every registered built-in, then called each adapter's `IsInstallValid()` and `IsImportValid(emptyDirectory)` methods.

| Probe | Result |
|---|---|
| Registry entries | 57 |
| Factory dispatch / adapter construction | 57/57 succeeded |
| `IsInstallValid()` with a unique, empty server-files path | 57/57 returned `false`; no exceptions |
| `IsImportValid()` with an empty temporary directory | 57/57 returned `false`; no exceptions |
| Existing installed game-server binaries found | None in the app's Debug or Release `servers` folders |
| Existing Test Explorer tests | None found in either project |

This verifies factory construction and the empty/missing-files validation paths only. **Install, update/validate against remote builds, Start, Stop, restart, and live queries were not run.** Those operations require actual game packages; downloading the full catalog can consume substantial bandwidth/disk, several titles require credentials or license keys, and launching each server would create processes and bind ports. I have not initiated those side effects without an installed game set and a controlled runtime test target. The feature matrix above remains a source-level capability assessment for those operations, not a claim that they passed live tests.

## Cross-cutting behavior and audit findings

### Start can hang or report readiness too early

`MainWindow.xaml.cs` marks a server `Starting` before calling the adapter. `Server_BeginStart` then loops while the process is alive and `ShowWindow` fails, without a timeout. A live process with no usable main-window handle can therefore leave the UI in `Starting` indefinitely. Conversely, once that method returns, the application labels a still-running process `Started` without checking that the game has bound its port or is queryable. This makes the UI state insufficient proof of a successful game startup.

Empyrion (`EGS`) has an additional per-game heuristic: it starts a launcher, waits for a Unity crash-handler command line, and extracts the server PID. If the child is not found after its retries, it returns failure; the launcher is not explicitly cleaned up. A long `Starting` period or orphaned launcher is therefore plausible.

### Stop is not uniformly graceful

The `Stop` column describes the adapter's request only. The manager polls for up to ten seconds and forcibly kills a process that has not exited; it then marks the server stopped and logs a notice if that fallback was needed. A successful UI transition to `Stopped` is not evidence that the game saved cleanly.

The following adapters call `Kill()` directly in their normal stop path: ARKSE, BlackWake, DayZ, Empyrion, Outlaws of the Old West, Onset, Stormworks, and The Forest. With embedded console enabled, Avorion, Eco, Insurgency: Sandstorm, Mordhau, Post Scriptum, Risk of Rain 2, Space Engineers, Squad, and Unturned also take a kill path (or a window-close path that may not reach a hidden process). Confirm save behavior before relying on Restart or scheduled shutdown for these.

Heat and Reign of Kings call `Task.Delay(5000)` without awaiting it, so their adapters do not actually wait the documented five seconds after sending `/shutdown`. The manager's later ten-second timeout is the only effective wait/fallback.

### Download, validation, and configuration status

1. **PocketMine-MP is the clearest current blocker.** Both hard-coded Jenkins artifact URLs now return a 301 redirect to `github.com/pmmp/PHP-Binaries/tags` (HTML), not the expected PHP ZIP or PHAR. The upstream repository's latest commit is explicitly an end-of-support announcement dated 2026-07-09. Installation should be disabled or replaced; update is especially unsafe because it deletes the existing PHAR before fetching the replacement. The current import/install validation mostly checks file presence, not that the downloaded file is a valid PHP runtime/PHAR.
2. **Mordhau's console default contradicts its own warning.** The source comment says `AllowsEmbedConsole` must be false because redirected output can freeze WindowsGSM and Mordhau on custom-map changes, but the field defaults to true. That makes the known-bad mode the default.
3. **Heat needs a manual SteamCMD/package check before support is claimed.** App ID `996600` has no public Steam app-details record. Its import/install validator checks `Heat.exe`, while Start also requires `Server.exe`, so a server can pass validation and still fail to launch. The stop delay is unawaited as noted above.
4. **Several import validators are weaker than Start prerequisites.** Besides Heat, MCPE checks the PHAR but not PHP/config; Bedrock checks the server executable but Start also requires `server.properties`; RCT2 checks only `openrct2.exe` and does not verify licensed game data; Mordhau validates a root executable while Start uses a nested shipping executable. Treat these as candidates for stronger validation, not confirmed failures on every installation.
5. **Vintage Story update is destructive if the replacement download fails.** It backs up the `data` directory, deletes and recreates the server-files directory, then reinstalls. The version check scrapes an AUR HTML page with a regex rather than using a versioned official API.
6. **“Validate” is not the same operation for every adapter.** SteamCMD adapters pass validation through to SteamCMD. For adapters whose `Update()` has no validation parameter, the manager falls back to a normal update; this refreshes/replaces the package rather than doing a file-integrity validation. Soldat is pinned to a fixed package version rather than tracking a moving latest release.
7. **Configuration errors can be hidden.** Many `CreateServerCFG()` implementations are `async void`; the install flow calls them without awaiting (except CFX) and catches configuration exceptions without surfacing them. RCT2, SCUM, and Unturned have empty config-generation methods. A logged install success therefore does not guarantee generated configuration is present or correct.
8. **Update success reporting is unreliable.** `GameServer_Update` logs a failure when the adapter reports an error, but returns `true` after the update branch regardless. Callers must inspect the log/error, not rely on that boolean as a success result.

### Shared UI functions

Restart is the app's stop-then-start composition; it inherits each adapter's stop risks. Kill is a global hard-kill action. Backup/restore are application-level file operations, not game-specific adapter functions. Query is optional and is skipped when `QueryMethod` is null. Source/GoldSrc addon management is shared, with DayZ as the other built-in addon case.

## Community signal and pruning guidance

For Steam titles, a nonzero count means Steam reported concurrent players at the snapshot; it does not measure dedicated servers, 30/90-day trends, or the size of a game's modding community. A zero (Onset) is not by itself proof of abandonment. The standout very-low-count snapshot entries are Onset (0), Deathmatch Classic (2), Outlaws of the Old West (2), Ricochet (3), Soldat (3), BlackWake (5), Reign of Kings (8), Zombie Panic! Source (9), Team Fortress Classic (13), Call of Duty 1 (36), Day of Defeat (65), Opposing Force (65), RCT2 (76), Insurgency (87), and Half-Life 2: Deathmatch (94). These are reasonable **review candidates**, not automatic removals.

Some non-Steam integrations have current upstream activity rather than a comparable player count: Mojang's manifest currently reports Java 26.3; the Bedrock API returns 1.26.52.3; Paper's API lists 26.3; OpenRCT2 released v0.5.6 on 2026-10-10; OpenTTD released 15.3 on 2026-04-04; Mindustry released v160.7 on 2026-10-08; and OpenRA had a commit on 2026-10-20 despite its latest stable release being older. These indicate project maintenance, not the number of active WindowsGSM server operators.
